# Photo Manager: third audit (code, UI, wording)

Date: 17 October 2026. Code audited: `main` at a14e03c, release 3.12.1. Nothing was changed in the repository; this report proposes fixes, it does not apply them.

## 1. Summary

This pass looked for what the two earlier audits (`AUDIT.md`, `audit_review.md`) missed, and added two things ALI asked for: a review of UI consistency and a review of every option label, help bubble and tool summary, with proposed rewrites and a design for editing the wording inside the app.

Headline numbers:

| | Count |
|---|---|
| New code findings (bugs, security, data safety) | 113 (1 critical, 17 high, 45 medium, 50 low) |
| UI consistency findings (from walking every screen) | 17 |
| Options reviewed for wording | 389 (plus 50 summaries, choice labels and group names) |
| Options with no help bubble today | 45 (all get one in the rewrite) |
| Baseline tests | 2427 run, all pass, 235 skipped (no Pillow-HEIF, no ffmpeg); `scripts/check.sh` prints `JS_OK` |

The twenty findings worth fixing first are in section 2. Everything else is grouped by area in sections 3 to 8, each with the file and line, what goes wrong, the proposed fix and the test to add. Section 9 is the UI consistency review, section 10 the wording review, section 11 the design for the in-app wording editor ("developer mode"), and section 12 an action plan written as prompts that can be handed to an agent one at a time.

What the earlier audits found that is now fixed in code (checked, not re-reported): the request body limit (old R1) and gzip on API answers (old S5). The other earlier items were not re-checked; this report lists only new findings.

### How this was done

- Baseline: full test suite and `sh scripts/check.sh` on a clean checkout with `PM_DATA` pointing at a temp folder.
- Six independent read-throughs of the code, one per area (core file operations; metadata and the index; server, API and login; the 50 tools; the page code; Windows, NAS, CLI and docs). Each finding was then checked against the source, and the ones marked CONFIRMED were reproduced on the sample library (`python -m app.cli demo`) or by reading the exact lines quoted. PLAUSIBLE means the code path is real but it was not run.
- A browser walk of every screen (Home, Photos, Places, Albums, People, Folders, Tools, each feature form, Setup, History, the viewer, the selection bar, the keyboard card) at desk and phone width, light and dark, with about 125 screenshots, to find inconsistencies a code read does not show.
- A dump of all 389 options (label, help, kind, group, Setup fallback, choices) and all 50 summaries, read in full for the wording review.

How to read a finding: **Where** gives `file:line` in the audited commit. **Fix** is a proposal; where two fixes are possible the recommended one comes first. **Test** names the test module and what the test asserts, following the project rule that every behaviour change comes with a test.

## 3. Core file operations and undo

### CO1. `tidy_empty_folders` deletes the share's Recycle Bin and walks above the task's root
- Severity: critical
- Status: CONFIRMED (experiment: share root holding only `#recycle/.../precious.jpg` + `@eaDir` -> 4 folders removed, `#recycle` and its contents gone). Re-verified by reading core/paths.py:411-460.
- Where: core/paths.py:411-412 (`LEFTOVERS` includes `#recycle`, `@recycle`), :432-460 (`tidy_empty_folders` loops upward with no stop). Callers: app/tasks/cull.py:261, duplicates.py:297, bydate.py:836, thin.py:251, develop.py:465, remirror.py:243, remirror_previews.py:163, unpair.py:182, videos.py:356, blur.py:250, undo.py:153.
- What happens: after a run empties a shoot folder, tidy walks up parent by parent. A share root (or an Inbox tree) that now holds only `#recycle` and `@eaDir` passes `only_leftovers`, so `shutil.rmtree('#recycle', ignore_errors=True)` wipes every recoverable delete on that share, then `os.rmdir` removes the share/tree root itself. Variant: undoing a Delete folder run leaves `#recycle` empty; undo.py:153 tidies `dirname(target)` = `#recycle` and `rmdir`s DSM's bin.
- Proposed fix: never remove a recycle folder (drop `#recycle`/`@recycle` from what is deleted; they may still count as "litter" for the emptiness test but must make the folder non-removable), give `tidy_empty_folders(folders, stop_at=root)` a boundary and stop at any Setup tree root; pass the scan root from each caller above; docs/DESIGN.md "Clean-up" section.
- Test to add: `tests/test_paths.py`: a tree `share/{#recycle/x.jpg,@eaDir,2022/Spain}`; `tidy_empty_folders({share/2022/Spain}, stop_at=share)` removes `2022/Spain` and `2022` only and `x.jpg` survives.

### CO2. Clean up deletes a tree outright while the plan says "the recycle bin"
- Severity: high
- Status: CONFIRMED (code)
- Where: app/tasks/cleanup.py:89-106 (`bins` only for roots that have one; blocked only if *none* has), :226-231 (`_target` returns "" for a root without a bin), :258-262 (`""` -> `shutil.rmtree`), :174 and :193-198 (stat "Where they go: the recycle bin" and the MOVED note whenever `bins` is non-empty).
- What happens: library on a share with `#recycle`, RAW tree on a share without. "Use the recycle bin" ticked. Plan says everything goes to the bin; apply moves the library piles and `rmtree`s the RAW piles permanently.
- Proposed fix: when `recycle` is ticked, a root with no bin becomes an error row ("Not cleaned - its share has no Recycle Bin") instead of a target of ""; show the destination per row; the stat should say "mixed" when it is. Files: cleanup.py only (+ tests/test_cleanup.py).
- Test to add: two roots, one with `#recycle`, `recycle=True`: the bin-less root's piles are refused and nothing under it is removed.

### CO3. Explorer rename silently overwrites an existing sidecar
- Severity: high
- Status: CONFIRMED (experiment: `a.RW2`+`a.xmp` renamed to `b.RW2` while `b.xmp` existed -> `b.xmp` content replaced, old `b.xmp` lost)
- Where: core/filesops.py:328-334 (`os.rename(side, stem+ext)` with no existence check; POSIX rename replaces), :335 (`_tell` omits the sidecar moves), :336 (returned dict has no `moves`, so the page cannot undo it).
- What happens: renaming a photo to a name whose `.xmp` already exists (an orphan sidecar from a deleted photo, or a RAW `b.RW2` whose `b.xmp` holds its stars) destroys that sidecar's rating/tags/GPS.
- Proposed fix: before renaming anything, compute all targets (file + sidecars) and refuse if any exists; return `moves` for all of them and pass them to `_tell`. Same check belongs in `core/renames.py`. Files: core/filesops.py, app/server.py (`do == "rename"` response), tests/test_filesops.py.
- Test to add: rename `a.RW2`->`b.RW2` with `b.xmp` present raises `Refused` and leaves all three files untouched.

### CO4. Delete stops half-way and loses the record of what it already moved
- Severity: high
- Status: CONFIRMED (experiment: JPEG moved into `#recycle`, then `Refused` for its RAW on a bin-less share; `b.jpg` gone from the library, no moves returned)
- Where: core/filesops.py:364-378 (`recycle_root` checked per file *inside* the move loop; `raise Refused` after earlier `shutil.move`s; any `OSError` from `shutil.move` also escapes), :379-384 (`acl.after_delete`, `_tell(gone=...)` and the `moves` return are all skipped). Same shape in core/quickedit.py:343-356 (an OSError mid-loop loses `moves`; a partner on a bin-less share is skipped with `continue` while the docstring promises "every copy").
- What happens: files are already in `#recycle` but the page gets a 409, History gets no record (server.py:2045-2052 runs only on success), Undo is never offered, and the index still shows the photos where they were.
- Proposed fix: resolve the bin for every file first and refuse before touching anything; wrap the loop so partial `moves` are returned (and recorded) on failure; quickedit.delete should report the copies it could not bin. Files: core/filesops.py, core/quickedit.py, app/server.py (record partial results), tests/test_filesops.py, tests/test_quickedit.py.
- Test to add: delete a JPEG whose RAW partner has no `#recycle` above it -> `Refused` and the JPEG is still in place.

### CO5. Explorer, viewer and Power-rename runs reach History without their moves, so Put it back is never offered
- Severity: high (undo exists only while the page's toast is visible)
- Status: CONFIRMED (code)
- Where: app/server.py:466-478 (FileJob builds `R.Result` without `moves`), :2045-2052 (explorer delete), :2104-2115 (renames.apply), :2192-2201 (viewer delete). `Result.moves` exists (app/registry.py:575) and runlog reads it (core/runlog.py:131).
- What happens: after an explorer move/delete or a 30-folder Power rename, History shows the run but `undo.plan` says "did not move any files"; the only undo is the client-held `body.moves`, which also means `filesops.undo`/`QE.undo` execute any `[from,to]` pair a client sends (fenced only by ALLOWED_ROOTS, never checked against a real record).
- Proposed fix: set `res.moves = got["moves"]` in the four places; have the undo routes take a run number and use `core.moves.put_back` (or verify the pairs against runlog). Files: app/server.py, app/web (undo button sends run no), docs.
- Test to add: `tests/test_server.py`: after `/api/files do=delete`, `runlog.recent()[0]["moves"]` is non-empty and `undo.plan({"no": n})` lists rows.

### CO6. `moves.shift(src, src)` renames the file to `_1`; bydate's RAW/preview rows and explorer moves can hit it
- Severity: medium
- Status: CONFIRMED mechanism (experiment: `shift(f, f)` -> `a_1.RW2`, recorded as a move); CONFIRMED for explorer (moving `a.jpg` onto its own folder -> `a_1.jpg`, `a_1.xmp`, "renamed 2"); PLAUSIBLE for bydate
- Where: core/moves.py:62 (`safe_target` sees the source itself as "taken"); app/tasks/bydate.py:452-467 (partner rows have no "already there" guard, unlike JPEG rows at :438); core/filesops.py:216-219 (`gather` has no same-folder guard for files).
- What happens: a RAW tree already in date shape (sorted earlier, or a re-run after a partial run) gets every negative renamed `X_1.RW2`, names drifting from their JPEGs; dragging files onto the folder they are in renames them.
- Proposed fix: in `shift`, return early when `normcase(abspath(src)) == normcase(abspath(dst))`; `gather` skips a file whose dirname is `into`; bydate `_move` skips when source == target. Files: core/moves.py, core/filesops.py, app/tasks/bydate.py, tests/test_moves.py, test_bydate.py, test_filesops.py.
- Test to add: `shift(r, p, p)` leaves `p` untouched and records nothing.

## 4. Metadata, sidecars and the index

All experiments were run on copies of `tests/fixtures/*` under the scratch dir with `PM_DATA` set there.

### MD1. Tag or label write destroys a JPEG's existing XMP packet when the packet sits past the first 256 KB
- Severity: high
- Status: CONFIRMED (experiment: a JPEG with five 60 KB APP2 chunks before its Lightroom-style XMP; `tagwrite.add(..., ["Rome"])` left one XMP segment containing neither `crs:CropTop`, the keyword `Italy` nor `xmp:Rating`)
- Where: core/jpegseg.py:135 (`xmp_packet` reads only `HEADER_BYTES`, no retry, unlike `exif_block` which retries to 4 MB); writers core/tagwrite.py:107 (`write_xmp_keywords`), core/labels.py:256 (`write_label_in_jpeg`); readers equally blind: core/tags.py:embedded_xmp, core/labels.py:written_label, core/places.py:written_place, core/iptc.py:datasets
- What happens: `xmp_packet()` returns "" for a packet beyond 262,144 bytes (large ICC/APP13/MPF before it), so a fresh packet is built; `_replace_segment` then scans the FULL file, finds the real packet and replaces it. Crop, develop settings, keywords and rating written by other programs are gone, silently. Reading side: such files show no tags, no label, no place.
- Proposed fix: make `segments()` report when it ran off the end of the buffer before SOS and have `xmp_packet`/`iptc.datasets` retry with `MAX_HEADER_BYTES` (mirror `exif_block`); in `write_xmp_keywords` and `write_label_in_jpeg` take the existing packet from `original` (already fully in memory). Same for `places.written_place`.
- Test to add: build a JPEG with >256 KB of APP2 ahead of an XMP packet carrying `crs:CropTop` and a keyword; `tagwrite.add` then assert both survive and `tags_of` lists the old keyword.

### MD2. A rating in the JPEG's own XMP packet is ignored on read and left stale on write
- Severity: high
- Status: CONFIRMED (JPEG with `xmp:Rating="4"` in its packet and no 0x4746: `rating_of` -> None, `read_rating` -> None)
- Where: core/exifwrite.py:584 (`rating_of`: sidecar then EXIF 0x4746 only), :527 (`read_rating`), :351 (`write_rating` touches only 0x4746); same blind spot in core/survey.py:_read_one (~190); core/facts.py:stars and the catalogue's `stars` column inherit it
- What happens: Lightroom, Bridge, darktable and digiKam write `xmp:Rating` into a JPEG's packet (Lightroom does not write the Microsoft 0x4746 tag), so a library rated there reads as unrated everywhere: index stars, Favourites, To develop, Send to develop, Library tab "rated" mark. Conversely `write_rating` leaves the old `xmp:Rating` in the packet, so Lightroom shows the previous value.
- Proposed fix: in `rating_of`/`read_rating` consult `sc.values_in(jpegseg.xmp_packet(path)).get("xmp:Rating")` between the sidecar and 0x4746; in `write_rating`, when a packet exists, also merge the rating into it and splice (as `write_label_in_jpeg` does). Update `survey._read_one` and DESIGN.md's rating-precedence text.
- Test to add: JPEG with `xmp:Rating="4"` in the packet only -> `rating_of == 4`; after `write_rating(5)` the packet says 5 and 0x4746 says 5.

### MD4. Files added or deleted outside the app are never picked up by the index loop
- Severity: medium-high
- Status: CONFIRMED by code reading

### SV1. No Origin/Host check on state-changing POSTs (CSRF / DNS-rebinding on the default, no-password install)
- Severity: high
- Status: CONFIRMED (curl)
- Where: app/server.py:1620-1630 (`_post`), :1057-1085 (`_read_body` accepts any Content-Type)

## 10. Wording review: labels, help bubbles and summaries

Written for the 389 options, 50 summaries and the choice labels in `app/tasks/*.py`. The same rules apply to GUIDE pages in `app/page.py` and to sentences the page builds in JavaScript.

### 10.1 What is wrong today

The current text is written in one person's literary voice. It is often witty and sometimes beautiful, but it is hard to read for a non-native speaker, and in places it does not say what the setting does. The recurring problems, with real examples from the code:

1. **The help does not say what the setting does.** It explains a trap, a history or an opinion instead.
   `undo.run`: "Nothing worth typing." `bydate.town_at_least`: "People. 0 names the nearest town whatever its size - honest, and it turns a week in Tuscany into eleven hamlets."
2. **Sentences with no subject, or the subject at the end.** `search.since`: "2022, 2022-07 or 2022-07-14." `exposure.folder`: "Everything underneath it is read."
3. **Idioms and metaphors.** "this is the belt" (geotag.keep_originals), "at its word" (bydate.shift_minutes), "a picture of nothing" (remirror_previews.orphans), "the cheap kind" (retime.keep_originals), "warming somebody's NAS".
4. **Dashes doing the work of full stops.** Most bubbles are one long sentence joined with " - ". Two or three dashes in one sentence are common.
5. **History and asides the user does not need.** "The Windows app asked this" (duplicates.keep), "as it always has" (brackets.tag), "which is what this task did before it could read a clip's capture time" (videos.shape), "the colour used to be left behind" (ratings.colours).
6. **CAPITALS for emphasis.** "Leave BLANK", "A folder NAME", "PATHS, not names", "Sync THIS folder", "writes NOTHING", "INSIDE the develop tree".
7. **Two names for one thing.** photo / photograph / picture / frame / shot / JPEG; negative / RAW; tool / feature / task / tab; folder / tree; stars / rating; colour / label; Setup / Settings; put aside / set aside / cull; clip / video; the tablet / the previews.
8. **Labels that are fragments of a sentence**, which only make sense next to the previous label: "to (mm)", "to f/", "to", "or longer than", "and those tags", "Called".
9. **Numbers without a unit on the label**, with the unit hidden in the help: "Join a shoot within" (hours), "Name the town within" (km), "Look for changes every" (minutes).
10. **The same help text copied to several tasks with small differences**, so they drift: the `mirror` flag has four different explanations; `in_file` has three.
11. **Help that describes a different control than the one shown**, e.g. `bydate.mirror` says "Without them the pairs still hold" but turning the flag off does not stop RAWs moving (see the tasks report).

### 10.2 The rules

**Labels** (the bold name beside a control)
- A noun phrase of one to four words that says what the box holds. Not a sentence, not a question, not a fragment that depends on the label above it.
- Put the unit in the label in brackets when the control is a number: "Give up after (minutes)", "Join a shoot within (hours)".
- Ranges get two complete labels: "Focal length from (mm)" / "Focal length to (mm)", never "to (mm)".
- Sentence case. No full stop. No capitals for emphasis.
- One name for one thing, everywhere (see the glossary).

**Help bubbles** (the text behind the "i" button)
- First sentence: what the setting does, in plain words, starting with the subject. "Photos below this rating are moved to _Culled."
- Second sentence (optional): what the default means, or what blank/0/-1 means. "Blank means the whole library."
- Third sentence (optional): one practical consequence or warning. "Start with the tag option; it moves nothing."
- Two to three short sentences, each under about 20 words. Full stops, not dashes. No semicolons.
- Say the value's unit and the allowed range when it is a number. Say where the value comes from when it is "(from Setup)".
- No history ("used to", "before", "the Windows app"). No jokes. No metaphors. No capitals for emphasis. No "honest", "worth", "simply", "exactly", "actually".
- Name other screens and tools by their exact titles, in the form "Setup > Colour meanings" or "the Find brackets tab".
- Use "you" for the person and "the app" for Photo Manager. Never "we".

**Summaries** (the line under a tool's name on the Tools screen and at the top of its form)
- One sentence, under 15 words, saying what the tool does: verb first, object, then where. "Moves low-rated photos and their RAWs into a _Culled folder."
- Add "Nothing is changed." only for report-only tools.

**Choice labels** (the entries of a drop-down or a tab row)
- Parallel grammar across the list. Either all nouns ("Year / month") or all short imperative phrases ("Tag them", "Move them aside").
- Say the consequence in the label only when the choices differ by consequence: "Tag them (nothing moves)".

**Group names** (the fold rows)
- One to three words, a noun: "Thresholds", "What moves with them" -> "Companion files". No "Advanced" and "More" both on one form.

## 11. Editing the wording inside the app ("developer mode")

ALI asked for a way to edit the wording in the software, then hand the result back so it can go into the source. This section is the design. It is not implemented.

### 11.1 What it is

A Wording tab under Setup, shown only when a developer switch is on. On it, every tool's title, tab name, summary, option labels, help bubbles, choice labels and group names can be edited in place. Edits are saved as overrides in `PM_DATA/wording.json`, applied wherever the text is shown (page, CLI `--help`), and exported as one file that can be sent back and merged into `app/tasks/*.py`.

### 11.2 How the text flows today

- Every string lives in the `Task(...)` and `Option(...)` declarations in `app/tasks/<name>.py`.
- `Task.describe()` (`app/registry.py:845`) and `Option.describe()` (`:91`) turn them into the JSON that `/api/tasks` (`app/server.py:1274`) sends; the page draws labels from `o.label` and the bubble from `o.help` (`script.js:1001-1003`).
- The CLI prints `o.help` under each `--option` (`app/cli.py:47-48`).
- `tests/test_wording.py` reads the registry directly and enforces: label at most four words; a one- or two-word label must have help or a group.

So there is one choke point: `describe()`. Overrides applied there reach the page and the API; the CLI needs a one-line change to read through the same function.

### 11.3 Design

**Storage.** `PM_DATA/wording.json`:

```json
{
  "version": 1,
  "edited": "2026-10-17T20:30:00",
  "overrides": {
    "cull.summary": "Moves low-rated photos, with their RAW files, sidecars and previews, into a _Culled folder.",
    "cull.option.min_stars.label": "Keep from (stars)",
    "cull.option.min_stars.help": "Photos rated below this are moved aside. 0 keeps everything.",
    "cull.option.mode.choice.tag": "Tag them (nothing moves)",
    "cull.group.Thresholds": "Limits",
    "geotag.title": "Add locations",
    "geotag.tab": "Locations"
  }
}
```

Keys are `task.field`, `task.option.<name>.<label|help>`, `task.option.<name>.choice.<value>`, `task.group.<old name>`. Only edited fields are stored; a field equal to the shipped text is removed from the file.

**A new module `core/wording.py`** (standard library only): `load()`, `save(overrides)`, `apply(task_dict)` which walks a `describe()` result and swaps in overrides, `shipped(task_name)` which returns the unmodified text for "Reset to shipped", and `export()` which returns the file plus, for each override, the shipped text and the `app/tasks/<file>.py` line it came from (found with `inspect.getsourcelines` on the task module and a text search for the shipped string), so the person merging it knows exactly where each line goes.

**Where it applies.**
- `Task.describe()` ends with `return wording.apply(result)`. One place; page, API and anything else that reads `describe()` get the overrides.
- `app/cli.py` `--help` reads labels and help through `task.describe()` instead of the raw `Option` objects.
- Tests keep reading the raw registry, so `test_wording.py` tests the shipped text and is unaffected by local edits. A second small test (`tests/test_wording_overrides.py`) checks the override file format, that `apply()` changes only the keys present, that unknown keys are reported not crashed, and that the four-word label rule is enforced on overrides too (the editor refuses to save a label of five words, with the same message the test gives).

**The developer switch.** A `developer` boolean in Setup under a folded "Developer" group, default off, with help "Shows the Wording tab under Setup, where the text of every tool can be edited and exported." Nothing else changes when it is on. (`PM_DEVELOPER=1` in the environment turns it on too, for a container.)

**The Wording tab** (`app/tasks/wording.py`, `settings=True`, `parent="setup"`, `tab="Wording"`, `hidden` unless the switch is on; the server already filters hidden tabs for the page):
- Top: a tool picker (the same list as Tools), a search box that matches any shipped or edited text, and three counters: "N edited, N with no help, N labels over four words".
- Body: one card per field in the order the form shows them. Each card shows the field name in small type ("cull › min_stars › help"), the shipped text greyed, and an edit box below with the current text. Edited fields get a coloured left edge and a "Reset to shipped" link. Labels get a live word count; help boxes get a live sentence count and a warning when a sentence is over 25 words or contains " - ", " – ", "ALL-CAPS" words or a banned word from the glossary (the style guide's rules, as a small list in `core/wording.py` so the test and the editor share it).
- Saving is per card (blur or Ctrl+S) through a new `POST /api/wording` `{key, text}`; `DELETE` resets one key. The page re-fetches `/api/tasks` after a save so the live form shows the new text immediately. A "Preview" link on each card opens that tool's form in the other pane with the bubble popped open.
- Bottom bar: **Download wording.json** (the export with shipped text and source locations, so it can be posted in this project and merged), **Upload wording.json** (replace or merge), **Reset everything** (asks first). The export is what ALI hands back; the merge into source is a mechanical pass an agent can do from it, since each entry names the file and the shipped string to replace.

**API.** `GET /api/wording` (the overrides plus, per key, the shipped text), `POST /api/wording` (one key or a whole file), `DELETE /api/wording?key=`. All three behind the login like every other write, and refused when the developer switch is off.

**What is out of scope for the first version, and how to add it later.**
- Page strings in `script.js` and `library/js` (about 400 user-visible literals such as "Delete to the recycle bin", "Nothing here yet", the dialog bodies). Phase 2 moves them into a `STRINGS` table (`app/web/page/strings.js`, loaded first) referenced as `S.deletePicked`, and the Wording tab gets a "Page" section that edits the same way; the server fills `{{STRINGS_JSON}}` in `index.html` with the shipped table plus overrides. `test_wording` then reads `strings.js`.
- GUIDE pages (`app/page.py`): the same table approach; GUIDE is already Python data.
- Translations: the override file is already the right shape for one language; a `lang` key per file would make it a translation file. Not planned, but the design does not block it.

### 11.4 Why this shape

- One choke point (`describe()`) means no option can be missed and no page or CLI code needs to know about overrides.
- Overrides, not edited source, so a release never loses local edits, the tests keep testing the shipped text, and the file is small and reviewable.
- The export carries the shipped text and the source location so merging is mechanical and can be checked: if the shipped text in the export does not match the source any more, the merge tool says so instead of guessing.
- The same rule list drives the test, the editor's warnings and the style guide, so the wording cannot drift back.

### 11.5 Estimated size

`core/wording.py` about 150 lines; `app/tasks/wording.py` about 60 lines (the form is drawn by the page from the Wording tab's own small script piece `library/js/20-wording.js`, about 250 lines, and `library/css/09-wording.css`, about 60 lines); three routes in `app/server.py` about 40 lines; `app/cli.py` 5 lines; `tests/test_wording_overrides.py` about 120 lines; CLAUDE.md, `docs/DESIGN.md` ("Wording lives in the declarations, and can be overridden") and CHANGELOG entries. Files touched: `core/wording.py` (new), `core/families.py` (the new tab under "setup"), `app/registry.py`, `app/tasks/__init__.py`, `app/tasks/wording.py` (new), `app/tasks/setup.py` (the switch), `app/server.py`, `app/cli.py`, `app/web/library/js/20-wording.js` (new), `app/web/library/css/09-wording.css` (new), `tests/test_wording_overrides.py` (new), `CLAUDE.md`, `docs/DESIGN.md`, `CHANGELOG.md`, `app/version.py`.
